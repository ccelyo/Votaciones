La vista de descomposición muestra cómo se divide el sistema en módulos (unidades de implementación) y qué responsabilidad tiene cada uno. Es una vista estática: no muestra procesos ni conectores en ejecución (eso es la vista C&C), sino cómo está organizado el código del repositorio. Los nombres de los componentes coinciden con los de la vista C&C para poder cruzar las dos vistas.

La jerarquía tiene cuatro niveles:

Nivel Elemento En el repositorio
0 Sistema Votaciones (espivota) El repositorio completo
1 Subsistema Agrupación lógica de componentes (presentación, comunicación, lógica, contratos)
2 Componente Una carpeta de primer nivel con su propio Dockerfile (ballot/, gateway/, …)
3 Módulo y submódulo Paquete o archivo de código (internal/token, app/services/login.py, …)

Descripción de las relaciones

  • Es parte de (contención). Es la única relación de la vista: cada módulo pertenece exactamente a un módulo padre, así que la descomposición forma un árbol. En el diagrama se representa anidando un recuadro dentro de otro.
  • Responsabilidad del módulo hoja (color). No es una relación entre módulos. Indica la responsabilidad principal del módulo: interfaz, dominio, acceso a datos, mensajería, seguridad y criptografía, cliente de otro servicio o arranque y soporte. Así se ve en cada componente la división API → lógica → persistencia → eventos que pide el plan del prototipo.
  • Encapsula un almacén (→ BD). Señala el único módulo de cada componente que accede a su base de datos. Ningún otro módulo, ni de otro componente, conoce esa base.
  • Usa. En las tablas de abajo, la columna Usa indica de qué módulos del mismo componente depende cada uno (según sus import). Las dependencias entre componentes no pasan por código compartido: ocurren en ejecución por HTTP o AMQP y se documentan en la vista C&C.

Descripción de los patrones arquitectónicos

  • Descomposición por capacidad de negocio (microservicios). Cada componente de nivel 2 corresponde a una capacidad (autenticar, emitir credenciales, firmar a ciegas, administrar urnas, recibir votos, escrutar, analizar, notificar). Es una carpeta independiente, con su lenguaje, sus pruebas y su imagen de contenedor, así que se construye y despliega sin tocar las demás.
  • Base de datos por servicio y ocultamiento de información. Solo un módulo por componente accede a su almacén (db/models, db/census, models.py, mongostore, store.rs, mongo-notification-repository). El esquema queda oculto detrás de ese módulo y ningún otro componente lo importa.
  • Capas dentro de cada servicio. Los servicios Python separan API (api/routes.py, api.py) → casos de uso (services/, service.py, rules.py) → acceso a datos (db/, models.py). Las dependencias van siempre hacia abajo.
  • Puertos y adaptadores (hexagonal). El dominio define interfaces y la infraestructura las implementa. En Notifications, domain, application e infrastructure están separados y index.ts hace de raíz de composición. En Ballot, ballot.CommitStore, ballot.VoteReader y ballot.SealedBallotReader son puertos que implementan mongostore o un adaptador en memoria para las pruebas.
  • API Gateway y Backend for Frontend. El Gateway es el único módulo con política transversal (jwt.ts, rateLimit.ts). El route handler app/api/[...path] del Servidor SSR es el BFF de la web: el navegador nunca conoce la URL del Gateway ni ve el token de sesión.
  • Publicar-suscribir. La mensajería vive en módulos propios (events.py, internal/events, internal/publisher, consumer.rs, rabbit-consumer.ts), separados de la lógica, y los contratos de eventos se versionan junto al código (docs/, CONTRACTS.md, events.rs).
  • Orquestador y tubería en Tally. internal/tally coordina pasos que no se conocen entre sí: ballotclient → decrypt → count → publisher.
  • Separación entre identidad y voto. Los módulos que conocen al votante (db/census, services/tokens) y los que reciben el voto (internal/token, internal/ballot) están en componentes distintos. La criptografía de la credencial se reparte entre el cliente (lib/m4, protocol/), Blind Signature (blind_rsa, key_store) y Ballot (token, receipt), de modo que ningún módulo puede unir un voto con un votante.

Coherencia con el código actual

  • Auth e Identity son componentes separados en la vista C&C, pero hoy se despliegan juntos en identity/. La descomposición en submódulos (Auth, Identity) y sus bases separadas permite extraer Auth a otro servicio sin reorganizar el código.
  • La vista C&C del prototipo 2 solo usa REST y AMQP, pero proto/ y los módulos pb/, clients/ballot_client.py e internal/server mantienen todavía el canal gRPC de administración entre identity y Ballot.
