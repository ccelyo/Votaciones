Estructura por capas

La vista por capas agrupa los componentes según su responsabilidad y define qué capa puede usar a cuál. Se presenta en dos niveles:

  1. Capas del sistema (figura anterior): cómo se organizan presentación, comunicación, lógica y datos, y qué dependencias hay entre ellas.
  2. Capas internas de cada componente (figura de más abajo): cómo se organiza cada servicio por dentro. Siguiendo el plan del prototipo, no se obliga a todos los servicios a tener las mismas capas internas: cuando un servicio no separa una capa, se indica.

Descripción de las relaciones

  • Puede usar (allowed-to-use). Una capa solo usa la inmediatamente inferior: presentación → comunicación → lógica → datos. Ninguna capa inferior conoce a una superior. Los servicios no llaman al Gateway ni a los clientes; responden a sus peticiones.
  • Uso dentro de la capa de lógica. Se permite en tres casos, todos síncronos e internos (no publicados por el Gateway):
    • Identity → Blind Signature (REST, con el secreto X-Internal-Token) para firmar a ciegas la credencial.
    • Identity → Ballot (gRPC) para registrar, cerrar y consultar urnas.
    • Tally → Ballot (REST, con un token compartido) para leer las papeletas cifradas de una urna cerrada.
  • Comunicación asíncrona por la capa 1. El resto de la coordinación entre servicios de lógica pasa por RabbitMQ, no por llamadas directas: Election publica election.*, Ballot publica votes.cast y consume election.*, Tally publica tally.completed, y Analytics y Notifications consumen esos eventos. Así los servicios de la misma capa no dependen unos de otros.
  • Propiedad de los datos. Cada almacén de la capa 1 lo usa un solo servicio, el que está encima en la figura. Tally no tiene almacén propio: lee de Ballot y publica su resultado.
  • Dentro de cada componente, cada capa interna usa solo las inferiores. La excepción intencional es la inversión de dependencias (▲): en Ballot y Notifications el dominio define la interfaz del repositorio (CommitStore, NotificationRepository) y la infraestructura la implementa, de modo que el dominio no depende de MongoDB.

Diferencias entre el diseño y el código actual

La figura muestra el código de main tal como está, incluidas tres diferencias que quedan pendientes:

  • Puente de capa de la CLI. La CLI usa por defecto http://localhost:8000 (identity) y http://localhost:8080 (ballot), con las rutas propias de esos servicios (/login, /elections/…), no las del Gateway (/api/auth/login, …). Se salta la capa de comunicación y, por tanto, la validación de JWT y los límites de tasa del Gateway. Para corregirlo, la CLI debe usar las rutas /api/* y apuntar al Gateway.
  • Election aún no recibe tráfico del Gateway. En docker-compose.yml, GATEWAY_ELECTION_URL apunta a identity (que conserva las urnas del prototipo 1), no al servicio Election.
  • identity.events no tiene productor. Analytics y Notifications se suscriben a census.updated, pero identity todavía no publica eventos.

Descripción de los patrones arquitectónicos

  • Arquitectura por capas (layered). Las cuatro capas del sistema separan presentación, comunicación, lógica y datos, y la relación «puede usar» va solo hacia abajo. Es una arquitectura por capas relajada en un solo punto controlado: los servicios de lógica pueden llamarse entre sí en los tres casos internos listados arriba.
  • Cliente-servidor y n niveles. Las tres interfaces son clientes de un único servidor lógico (el Gateway). Cada capa se despliega en sus propios contenedores, así que las capas lógicas coinciden con niveles físicos separados.
  • API Gateway. La capa de comunicación concentra las políticas transversales (JWT, CORS, límites de tasa) para que los servicios de lógica no las repitan y los clientes conozcan un solo punto de entrada.
  • Backend for Frontend. Dentro de la capa de presentación, el Servidor SSR es el backend del Cliente navegador: le sirve las páginas y reenvía /api/* al Gateway. Así el navegador no conoce la URL del Gateway ni el JWT, que se guarda en una cookie httpOnly.
  • Base de datos por servicio. En la capa 1, cada almacén pertenece a un único servicio de lógica, lo que permite elegir la tecnología adecuada a cada uno (PostgreSQL para datos relacionales, MongoDB para papeletas y proyecciones).
  • Publicar-suscribir. RabbitMQ desacopla a los servicios de la capa de lógica: el productor no conoce a sus consumidores, y un consumidor caído no bloquea al productor (colas duraderas con DLQ).
  • Capas internas y arquitectura hexagonal. Cada servicio repite la separación interfaz → aplicación → dominio → infraestructura. En Notifications y Ballot se aplica además la inversión de dependencias de la arquitectura hexagonal (puertos y adaptadores).
